## 1. 이번 작업의 결정

**상품 탐색 → 투자 → 보유 관리 → 회수가 이어지는 제품으로 다시 설계한다. 기존 화면, 조형물, 배치, 컴포넌트를 보존할 의무는 없다.**

사용자는 기존 디자인을 버리는 것까지 포함한 재설계를 요청했다. 이 문서는 과거 Clearform 유지 및 검증 체험 중심 계획을 새로운 디자인 방향으로 대체한다. 보안, 데이터 검증, 운영 설정에 관한 기존 규칙은 유지한다. 문서 작성 자체가 실제 투자 기능 구현이나 출시 완료를 의미하지 않는다.

첫 대상은 GMD USTX 한 상품이다. 단, 현재 모델 바스켓의 명칭을 그대로 거래 가능한 상품으로 바꾸지 않는다. 해당 자산을 실제로 취득·보관·회수할 수 있는 구조가 확인되어야 한다. 이 경로를 지원할 수 없다면 거래 가능한 최초 상품의 범위를 먼저 조정한다.

주 사용자는 구성과 비용을 확인하고, 투자 후 자신의 자산과 진행 중인 거래를 관리하려는 사람이다. 개발자나 심사위원에게 계산 검증을 체험시키는 동선은 보조 영역으로 이동한다.

### 완료의 의미

- 디자인 완료: 첫 방문, 상품 판단, 거래 입력, 처리 중, 완료, 실패, 재방문의 화면이 같은 체계로 연결된다.
- 프론트 완료: 실제 상태와 권한에 따라 화면이 변하며 새로고침·뒤로 가기·재접속에도 거래 문맥이 유지된다.
- 제품 완료: 입금 확인 → 자산 취득 → 보유 반영 → 회수 요청 → 지급 확인까지 기록이 일치한다.
- 운영 출시: 위 흐름을 의도한 거래 경로의 테스트 환경에서 확인한 뒤 실제 자산 취급·운영 준비를 별도로 충족한다.

디자인은 백엔드 결정과 병행할 수 있다. 구매 버튼만 있는 화면이나 로컬 모의 데이터로 제품 완료를 선언하지 않는다.

## 4. 시각 디자인 방향

### 4.1 인상과 고유한 표현

방향은 **절제된 금융 작업 화면**이다. 차가운 중성 배경, 진한 글자, 명확한 조작 영역을 사용한다. 상품의 개성은 장식 이미지보다 실제 구성 자산과 비중으로 만든다.

Ganymede의 반복되는 시각 요소는 **바스켓 구성 띠 + 같은 순서의 보유 자산 행**이다. 구성 띠에서 AAPLx를 선택하면 해당 행과 기여 가치가 연결된다. 상품 상세에서 보던 자산의 순서·표기를 내 보유 상세에서도 유지한다. 색상만으로 종목을 구분하지 않고 이름·수치·선택 상태를 함께 표시한다.

큰 제목과 장식 중심 홈, 모든 항목을 동일한 둥근 카드에 넣는 배치는 사용하지 않는다. 상품 비교는 행, 거래 입력은 하나의 패널, 이력은 시간순 목록으로 표현한다.

### 4.2 기본 토큰 초안

| 요소 | 제안 | 적용 원칙 |
| --- | --- | --- |
| 배경 | `#F3F5F6` | 화면 전체의 조용한 바탕 |
| 표면 | `#FFFFFF` | 거래 입력과 집중해서 읽는 영역 |
| 주 글자·헤더 | `#172B35` | 어두운 헤더와 밝은 본문으로 역할 구분 |
| 보조 글자 | `#526570` | 설명과 시간. 핵심 금액을 연하게 만들지 않음 |
| 주 행동 | `#0B625B` | 투자·확인 등 주요 행동에 제한적으로 사용 |
| 경계 | `#D5DEE2` | 데이터 행·입력 영역 등 필요한 구분 |

성공·주의·오류는 별도 의미 토큰으로 둔다. 브랜드 색과 수익의 증가·감소 색을 혼동하지 않는다. 위 값은 시안 시작점이며 실제 조합의 대비를 확인한 후 확정한다.

- 본문·입력: Source Sans 3, 16px 기본. 보조 문구 14px, 중요한 거래 정보는 축소하지 않는다.
- 제목: Instrument Sans, 페이지 32–40px, 구역 22–26px. 큰 제목으로 첫 화면을 소모하지 않는다.
- 주요 금액: 40–48px, 모바일 32–36px. 표 금액 16px, 자릿수 고정 폭·오른쪽 정렬.
- 기존 제목 자간·단어 간격에 대한 Claude 수정은 임의로 덮어쓰지 않는다. 새 화면은 크기·줄 길이·배치로 먼저 해결한다.
- 간격: 관련 항목 8–12px, 묶음 24px, 큰 구역 32–40px. 빈 공간을 채우기 위한 장식 카드를 추가하지 않는다.
- 모서리: 입력·버튼 8px, 주문 패널 12px. 그림자는 떠 있는 메뉴·패널에만 제한한다.
- 기본 버튼 높이 44–48px. 색만 바뀌는 텍스트를 핵심 버튼처럼 사용하지 않는다.

### 4.3 너비와 밀도

- 데스크톱 내용 폭은 최대 1440px, 좌우 여백 24–48px. 1440px 화면에서 핵심 상품 정보와 다음 행동이 함께 보이게 한다.
- 2560px 이상에서도 본문을 끝없이 늘리지 않는다. 중앙의 가격·구성·주문 영역이 읽기 어려울 만큼 작아지지 않도록 확인한다.
- 상품 상세는 12열 기준 정보 8열, 주문 4열. 주문 영역은 약 340–400px에서 읽히게 한다.
- 두 영역이 최소 폭을 확보하지 못하면 한 열로 전환한다. 내용이 깨지는 지점에 맞춰 분기한다.
- 모바일은 16–20px 여백, 상단 계정 영역, 하단 3개 주요 메뉴. 주문 중에는 하단 영역의 역할을 전환해 메뉴와 주문 버튼이 겹치지 않게 한다.

## 5. 정보 구조와 이동 규칙

```text
Ganymede
├─ Markets / 상품                    /
│  └─ USTX 상품 상세                /products/ustx
│     ├─ 구성·가격·비용·이용 조건
│     ├─ 투자 절차
│     └─ Transparency              /products/ustx/transparency
├─ Portfolio / 내 자산              /portfolio
│  └─ 보유 상세 → 추가 투자 / 회수
├─ Activity / 거래 내역             /activity
│  └─ 거래 상세                     /activity/[id]
└─ 보조 영역
   ├─ Lab                          /lab
   ├─ 방법론·이용 조건
   └─ 운영 화면                    권한 있는 사용자만
```

- 최상위 메뉴는 Markets, Portfolio, Activity 세 개로 통일한다. 어느 화면에서도 순서가 바뀌거나 메뉴가 사라지지 않는다.
- 홈과 Markets를 별개의 유사 화면으로 만들지 않는다. 첫 방문에는 상품 이해, 재방문에는 상품 상태 확인을 돕는 같은 진입점이다.
- 상품 하나인 초기 버전에는 가짜 상품 목록, 무의미한 검색·필터를 넣지 않는다. 상품이 늘면 행 구조를 확장한다.
- 비로그인 상태에서도 상품은 읽는다. 투자 시작 또는 내 자산 접근 시 계정 연결로 이어진다.
- 지갑 연결과 계정 확인을 구분한다. 네트워크 변경은 그 네트워크가 필요한 거래 단계에서 이유와 함께 요청한다.
- 각 화면은 주소로 직접 열 수 있고 뒤로 가기가 작동한다. 입력 문맥은 유지하되 서명·주문을 새로고침으로 재실행하지 않는다.
- 투명성 상세에서 돌아오면 원래 상품 또는 보유 상세로 복귀한다. 홈에서 다시 탐색하게 만들지 않는다.
- 거래 완료 후 기본 행동은 `내 자산 보기`, 처리 중이면 `거래 진행 보기`다.

## 6. 화면별 상세 설계

### A. 공통 헤더·메뉴·계정

**목적:** 현재 위치, 계정, 사용 환경을 항상 이해하게 한다.

- 왼쪽 G 로고, 가운데 세 메뉴, 오른쪽 네트워크/계정 영역.
- 테스트 환경은 하나의 지속적인 표시로 식별하고 거래 확인에도 다시 명시한다. 모든 단락에 같은 설명을 반복하지 않는다.
- 미연결·연결 중·연결됨·다른 네트워크·계정 변경·연결 오류를 구분한다.
- 계정이 바뀌면 이전 잔액·견적을 즉시 무효화하고 새 계정 상태를 불러온다.
- 모바일·문서 페이지에서도 같은 메뉴 체계를 유지한다.
- 완료 기준: 홈·상품·내 자산·거래·투명성·문서 사이에서 탐색 방식이 변하지 않는다.

### B. Markets / 상품 홈

**목적:** 무엇을 다루는 상품이며 무엇으로 구성되는지, 지금 이용 가능한지 판단한다.

```text
구성 자산과 비중          비용·매수/회수 조건 요약          투명성 상태
```

- 주 행동은 `상품 상세 보기`. 거래 가능한 상품이면 상세 안에서 `투자하기`로 이어진다.
- 가격은 의미에 따라 `최근 발행 NAV` 등으로 표시한다. 거래 견적과 같은 숫자로 취급하지 않는다.
- 가격 이력은 실제 기록 범위만 사용한다. 24시간이 없으면 24시간 수익률을 만들지 않는다. 이력이 부족하면 최근 값과 구성 내역을 배치한다.
- 첫 화면에서 구성 종목, 가격 기준, 이용 상태, 주 행동을 확인한다. 수익률·TVL·이용자 수를 장식 숫자로 채우지 않는다.
- 소개는 2–3줄. 거대한 슬로건과 검사 체험 섹션은 제거한다.
- 로딩은 정보 위치를 예약한 정적 스켈레톤. 실패 시 상품 설명은 유지하고 값 영역에만 읽기 실패·재시도를 표시한다.
- 완료 기준: 1440×900 및 390×844에서 상품명·구성 대상·이용 상태·다음 행동을 스크롤 전에 식별한다.

### C. USTX 상품 상세

**목적:** 구매 판단에 필요한 정보와 다음 행동을 같은 문맥 안에 놓는다.

```text
상품 > US Tech Basket
US Tech Basket / USTX                         [이용 가능 상태]

┌─ 정보 영역 ──────────────────────────┬─ 주문 영역 ───────────┐
│ 최근 NAV / 기준 시각                 │ 투자 금액             │
│ 실제 가격 이력                       │ 결제 자산 / 사용 가능액│
│                                      │ 견적·수수료·최소수령량 │
│ [구성] [비용·운용] [투명성]           │ [검토하기]            │
│ 자산 / 실제 비중 / 기준 가격 / 기여액 │ 가격 기준과 만료 시각  │
└──────────────────────────────────────┴───────────────────────┘
```

- 상단: 이름·티커·구성·가격 시각·이용 상태. 검증 결과는 이보다 높은 시각적 우선순위를 갖지 않는다.
- 본문: 가격 이력 → 구성 → 비용·운용 → 투명성/조건. 필수 비용·회수 제한은 탭을 열어야만 알 수 있게 숨기지 않는다.
- 현재 비중과 목표/고정 시점 비중을 구분한다. 6개 자산을 거대한 카드 6개로 만들지 않고 한 표에서 비교한다.
- 자산 선택 시 가격 기준·기여액을 같은 영역에 펼친다. 상세를 보려면 외부 사이트로 나가야 하는 구조를 피한다.
- 주문 패널: 지원 결제 자산, 실제 사용 가능 잔액, 금액, 비용, 예상/최소 수령량, 견적 만료. 확인되지 않은 값은 0으로 표시하지 않는다.
- 거래 미지원이면 같은 자리에 이유와 가능한 다음 행동을 제시한다. 비활성 버튼 하나만 놓거나 가짜 주문 성공을 만들지 않는다.
- 모바일: 가격·구성 요약 다음 `투자하기`로 주문 화면 진입. 핵심 조건과 입력이 키보드·고정 메뉴에 가리지 않는다.
- 완료 기준: 조건 확인을 위해 이동해도 입력 문맥이 유지되고 만료된 견적은 다시 검토한다.

### D. 투자 입력·검토·진행·완료

**목적:** 무엇을 지불하고 무엇을 받는지, 지금 어느 단계인지 안다.

1. 입력: 상품·결제 자산·금액·사용 가능 잔액. 전액 사용은 수수료용 잔액 필요 여부를 반영한다.
2. 검토: 지불 총액, 수령 자산/지분, 수수료, 가격 조건, 처리 방식, 환경. 확인 버튼에 실제 다음 행동을 명시한다.
3. 지갑 단계: 자산 사용 승인과 구매 서명을 구분한다. 어디에서 확인해야 하는지 안내한다.
4. 진행: 제출됨 → 입금 확인 → 자산 취득/정산 → 보유 반영. 실제 백엔드 경로에 없는 단계를 연출하지 않는다.
5. 완료: 확인된 수령 수량, 지불액, 완료 시각, 거래 식별자. `내 자산 보기`로 이동한다.

- 지갑 거절을 실패한 입금으로 표시하지 않는다. 아직 전송되지 않은 단계임을 설명하고 입력을 유지한다.
- 전송 후 응답이 끊기면 `결과 확인 중`으로 기존 거래를 조회한다. 즉시 같은 주문을 다시 보내도록 유도하지 않는다.
- 입금 뒤 매수가 실패하거나 일부만 처리되면 남은 금액·처리 수량·복구/반환 상태를 보여준다. 빨간 오류창으로 끝내지 않는다.
- 진행 화면을 닫아도 Activity에서 이어 본다. 시간이 지났다는 이유로 완료를 표시하지 않는다.
- 완료 기준: 거절·만료·통신 단절·재접속·중복 클릭이 거래나 보유를 중복 생성하지 않는다.

### E. Portfolio / 내 자산

**목적:** 보유 자산과 처리 중인 금액을 구분하고 관리한다.

```text
내 자산                                      [계정 / 기준 시각]
총 평가액                  확인 가능한 손익       처리 중인 거래

보유 상품       수량       평가액       취득 원가/손익       행동
USTX            …          …            …                 [상세]

최근 거래                                          [전체 내역]
```

- 총 평가액, 보유 수량, 거래 대기 금액을 분리한다. 미처리 입금을 보유 자산과 더해 이중 계산하지 않는다.
- 원가가 확인되지 않으면 손익을 만들지 않는다. 일부 가격이 없으면 완전한 합계처럼 표현하지 않는다.
- 보유 상세는 상품 페이지와 같은 구성 언어를 사용한다. `추가 투자`, `회수`는 해당 보유와 연결한다.
- 미연결은 계정 연결 안내, 보유 없음은 상품 탐색, 처리 중은 기존 거래 진행 상태로 각각 다르게 표현한다.
- 조회 실패는 0원으로 대체하지 않는다. 이전 값이 있으면 시각과 함께 표시하고 재조회한다.
- Paper lab의 쿠키 기반 보유를 실제 내 자산으로 이전하거나 이름만 바꾸지 않는다.
- 완료 기준: 재방문 시 보유·대기 거래·가능한 행동을 한 화면에서 확인한다.

### F. 회수

**목적:** 얼마를 회수하고 어디로 언제 받는지 예측한다.

- 보유 상세 → 수량 입력 → 수령 자산·목적지·비용·조건 검토 → 서명 → 처리 상황 → 지급 확인.
- 사용 가능 수량과 회수 중인 수량을 구분한다.
- 예상 수령과 확정 수령을 구분하고 지분 소각만으로 `회수 완료`를 표시하지 않는다.
- 지연·부분 지급·실패 시 실제 단계와 남은 수량/금액을 표시한다. 조회·재시도·지원 중 실제 가능한 다음 행동을 제시한다.
- 완료 기준: 지급 확인과 보유 감소가 같은 거래 기록으로 설명된다.

### G. Activity / 거래 내역

**목적:** 거래가 사라지지 않고 현재와 과거 상태를 이해한다.

- 시간, 상품, 투자/회수 종류, 금액, 상태를 행으로 표시한다. 초기에는 복잡한 검색·필터를 넣지 않는다.
- 처리 중인 항목은 상단, 완료된 거래는 시간순으로 둔다.
- 항목 선택 시 별도 주소가 있는 거래 상세. 모바일과 직접 링크도 같은 내용을 제공한다.
- 실제 단계, 최근 업데이트 시각, 입력/출력 금액, 비용, 관련 거래 링크, 가능한 다음 행동을 표시한다.
- 재접속해도 같은 ID로 이어 본다. 계정이 바뀌면 이전 계정의 이력을 섞지 않는다.
- 완료 기준: 통신 중단 후 결과를 찾기 위해 새 주문을 만들 필요가 없다.

### H. Transparency / 투명성 상세

**목적:** 관심 있는 사용자가 가격과 구성 기록의 근거를 확인한다.

- 상품명 → 기록 기준 NAV·시각 → 확인 결과 → 구성·산식 → 발행 이력 → 기술 상세 순서.
- `기록과 계산 일치`, `아직 확인하지 못함`, `불일치`처럼 명확한 문구. 가격 최신성은 별도 상태다.
- 문서·해시·직접 RPC 결과의 의미를 한 문장으로 설명하고 세부 체크는 펼쳐 본다.
- 가격 평가 시도, 개별 가격 기준, 온체인 기록 시각을 하나의 `Updated`로 뭉개지 않는다.
- 검증은 진입 시 자동 수행한다. 불일치는 거래 판단에 영향을 주는 문맥에서 숨기지 않는다.
- 가격 변경 실험과 합성 문서는 Lab으로 옮긴다. 해시 일치를 실제 보관 증명으로 표현하지 않는다.
- 완료 기준: 기술 용어를 몰라도 결과와 한계를 이해하고 원하면 근거에 접근한다.

### I. Lab·문서·운영·오류

- Lab: 모의 전략·검증 실험을 유지하되 지속적으로 모의 환경임을 표시. 주 메뉴와 실제 Portfolio에서 분리한다.
- 문서: 비용·회수 조건·운용 방식을 일관된 읽기 레이아웃으로 제공하고 상품 상세로 돌아가는 경로를 둔다.
- 운영: 고객 메뉴에서 분리. 링크 숨김으로 권한 검사를 대신하지 않는다.
- 404: 상품/내 자산 복귀. 서비스 오류: 가능한 화면 유지·재시도. 거래 중 오류: 기존 거래 ID·진행 조회 경로 보존.

## 7. 모션 설계

**정적인 인상을 없애되 읽고 있는 숫자와 입력 영역은 안정적으로 유지한다.** 실제 구성, 사용자 선택, 거래 단계 변화에 반응을 집중한다.

| 위치 | 반응과 목적 | 시작값 | 움직임 줄이기 |
| --- | --- | --- | --- |
| 첫 상품 진입 | 구성 띠가 한 번 드러나며 6개 자산 관계를 보여줌 | opacity + 띠의 짧은 clip reveal, 240ms | 즉시 표시. 추가 지연 없음 |
| 자산 선택 | 비중 띠·해당 행 강조, 기여값 교체 | 강조 160ms, 내용 opacity 160ms | 이동 없이 강조 |
| 메뉴·탭 | 선택 즉시 변경, 필요 시 내용 교체 | opacity 150ms | 즉시. 포커스 지연 없음 |
| 버튼 | 눌림 확인 | transform 0.98, 100ms | 색·경계만 변경 |
| 주문 검토 | 입력에서 검토로 이어지는 관계 | translate 12px + opacity, 240ms | opacity 120ms 또는 즉시 |
| 진행 단계 | 실제 확인된 단계 표시 | opacity 180ms | 즉시 결과 표시 |
| 데이터 갱신 | 바뀐 값의 위치를 약하게 강조 | 텍스트 즉시, 강조 opacity 200ms | 짧은 정적 강조 |
| 상세 펼치기 | 하위 정보 위치 유지 | opacity 160ms, 높이 연출은 필요 시만 | 즉시 펼침 |

- 진입 곡선 `cubic-bezier(0.23, 1, 0.32, 1)`, 같은 요소 이동 `cubic-bezier(0.77, 0, 0.175, 1)`.
- CSS transition 우선. 단순 페이드 때문에 모션 라이브러리를 추가하지 않는다.
- 반복 부유, 마우스를 쫓는 금융 데이터, 자동 스크롤, 숫자 카운트업, 가짜 진행률, 모든 카드의 순차 등장은 사용하지 않는다.
- 빠른 재클릭·닫기·뒤로 가기로 취소 가능. 키보드·포커스를 애니메이션 완료까지 기다리게 하지 않는다.
- 로딩은 정적 자리 표시와 상태 문구를 기본으로 한다. 완료 모션은 실제 완료 이벤트로만 실행한다.

## 8. 데이터·상태 계약

필요한 프론트 계약의 초안이며 현재 API가 모두 제공한다는 뜻은 아니다. 필드명·거래 단계는 백엔드 담당과 맞춘다.

| 화면 정보 | 필요한 근거 | 없을 때 표현 |
| --- | --- | --- |
| 거래 가능 여부 | 상품·계정·네트워크별 허용 여부와 이유 | 이유와 행동 제한 |
| NAV | 값, 통화, 유효 시각, 출처 | 읽기 실패 또는 마지막 값+시각 |
| 현재 구성 비중 | 같은 시점의 구성/가격 | 목표 비중과 구분하거나 현재 비중 없음 |
| 거래 견적 | ID, 입력/출력 자산·수량, 비용, 만료, 실행 조건 | 확정·서명 진행 불가 |
| 주문 진행 | 계정에 귀속된 ID, 단계, 업데이트, 재시도 가능 여부 | 마지막 확인 상태와 조회 경로 |
| 내 보유 | 실제 수량, 보류 수량, 기준 시각, 확인 가능한 원가 | 수량/평가/손익 결손을 개별 표시 |
| 회수 완료 | 지급/전달 확인과 수령량 | 현재 지급 단계 유지 |
| 투명성 결과 | 문서·계산·체인 확인과 각각의 시각 | 최신 가격·보관·거래 가능으로 확대 해석하지 않음 |

- 읽기 상태: loading / ready / empty / stale / unavailable 구분.
- 거래 상태: 지갑 입력 대기, 제출, 처리 중, 완료, 거절, 복구 필요. 백엔드 상태를 임의로 성공으로 축약하지 않는다.
- 가능한 행동도 응답에 근거한다. `canRetry`, `requiresAction` 등의 실제 의미를 정한다.
- 금액은 기존 정수 단위 유지. 지불 자산, NAV 표시 통화, KRW 모의 금액을 혼합하지 않는다. 환산에는 환율 출처·기준 시각이 필요하다.

## 9. 모바일·접근성·읽기 규칙

- 모바일은 상품명·상태·가격·주 행동 → 구성 → 상세 순으로 재배치한다.
- 보유 표는 종목·수량·가치를 한 묶음으로 전환하고 보조 열은 상세로 옮긴다. 행동을 가로 스크롤 끝에 두지 않는다.
- 고정 헤더·메뉴·버튼은 안전 영역과 키보드를 고려한다. 확대 시 필요하면 고정을 해제한다.
- 상태는 색·아이콘·문구를 함께 사용한다. 입력 오류와 비활성 이유가 식별되어야 한다.
- 중요 상태 변경은 보조 기술에도 알리되 가격 갱신마다 반복 낭독하지 않는다.
- 다이얼로그 이름, 포커스 진입·복원, Escape, 배경 접근 제한을 포함한다.
- 제품 언어는 우선 현재 영어 유지. UI는 sentence case로 통일하고 불필요한 대문자 라벨·번호 장식을 없앤다.
- 검수 폭: 360, 390, 768, 1024, 1440, 1920, 2560px. 200%·400% 확대와 실제 reduced-motion 설정은 변경된 화면을 대상으로 확인한다.
- Claude가 끝낸 이전 화면 검사를 반복하지 않는다. 재설계로 바뀐 화면과 공통 요소 영향 범위를 새로 확인한다.

## 10. 구현 구조와 협업 경계

### 프론트·디자인

- 공통 셸, 메뉴, 상품 홈·상세, 주문 검토, 진행·복구, Portfolio, Activity, Transparency.
- 공유 요소: 금액/시각, 이용 상태, 데이터 상태, 구성표, 거래 요약·단계, 계정 연결.
- `HomeClient.tsx`의 여러 화면 분기를 고객 화면·Lab·운영으로 분리. 주소·페이지 상태의 소유권을 명확히 한다.
- `clearform.css` 위에 계속 누적하지 않고 공통 토큰과 화면/컴포넌트 범위 스타일로 교체. 한 화면에는 한 체계를 적용한다.
- UI 데이터 어댑터에서 현재 공개 데이터와 미래 거래 상태를 분리. 미구현 상태는 로컬 시안의 명시적 fixture로만 사용한다.
- 금액·검증 함수는 재사용하며 기존 보호 로직을 제거하지 않는다.

### 백엔드 담당과 연결할 일

- 최초 상품·결제 자산·지원 체인·취득·보관·회수 경로.
- 계정/지갑 확인, 실행 견적, 입금 확인, 중복 방지, 보유 정합성, 지급 확인, 실패 복구.
- 가격 이력 범위·상품 상태 계약. 검증 결과가 어떤 거래를 중단해야 하는지 제품 정책과 맞춘다.
- Claude 담당 `lib/engine`, `lib/xstocks`, `relayer`, `app/api`는 디자인 계획의 직접 수정 범위가 아니다. 인터페이스 요구사항을 문서로 전달하고 통합 시 연결한다.

새 브랜드 네이밍, 여러 상품 확장, 추천 알고리즘, 복잡한 분석 대시보드, 네이티브 앱은 추가하지 않는다. 상품 하나의 완결된 사용 경험에 집중한다.

## 11. 단계별 실행 순서

종료 기준은 자체 검수 기준이다. 매 단계 사용자 승인을 요구해 멈추는 절차가 아니다. 구조를 바꿔야 하는 새로운 제품 결정이 생기면 이유와 선택지를 구체적으로 제시한다.

| 단계 | 할 일 | 결과물 | 넘어가는 기준 |
| --- | --- | --- | --- |
| 1. 제품 경로 고정 | 지원/미지원 경계, 최초 상품·결제·보관·회수 결정, 상태 계약 | 고객 여정·거래 상태표·담당 경계 | 입금부터 지급까지 누가 무엇을 확인하는지 명확함. 미정은 표시 |
| 2. 실제 화면 설계 | Markets, 상품 상세+주문, 보유 상세, 거래 상세를 공통 체계로 설계 | 데스크톱 핵심 4개 시안, 모바일 상품/주문/자산 시안, 실패 상태 | 장식 없이 상품/행동/상태가 명확하고 화면별 정보 구조가 읽힘 |
| 3. 셸·상품 구현 | 메뉴·토큰·반응형, 홈·상세·구성표·실제 가격 이력, Transparency 재배치 | 읽기 동선이 완성된 로컬 프리뷰 | 검증을 거치지 않아도 상품 이해와 주 행동 도달 |
| 4. 투자·회수 구현 | 계정 상태, 입력·검토·지갑, 진행·복구·지급 | 실제 상태 계약과 연결된 거래 흐름 | 만료·거절·중복·단절이 정상 진행과 같은 수준으로 처리됨 |
| 5. 자산·거래·모션 완성 | 보유·이력·재접속, 선택/진행 모션, Lab 분리, 이전 주소 연결 | 전체 고객 여정과 레거시 이동 경로 | 한 거래가 상품→보유→회수→이력에서 일관됨 |
| 6. 통합 검수·출시 준비 | 실제 경로 테스트, 변경 화면의 모바일·접근성, Claude 변경 통합 | 검수 기록·배포 가능 변경 묶음·되돌리기 기준 | 화면의 약속과 실행이 일치하고 회귀 문제 해소 |

1단계에 미정 백엔드 항목이 있어도 2–3단계 설계는 진행 가능하다. 미정 조건을 확정된 UI 문구로 쓰거나 4단계 연결 완료로 표시하지 않는다. 첫 시안은 홈 한 장에 그치지 않고 상품·자산·거래를 함께 보여 방향의 일관성을 확인한다.

## 12. 검수 기준

### 시각·동선

- 첫 화면에서 상품 정체, 환경, 이용 상태, 다음 행동을 식별한다.
- 금액과 버튼이 장식·긴 제목·중복 안내 아래로 밀리지 않는다.
- 상품 상세에서 비용·회수 조건을 찾고 거래 검토에서 다시 확인한다.
- 상품명·통화·수량·상태가 모든 화면에서 같은 의미다.
- 메뉴가 바뀌지 않고 직접 링크·새로고침·뒤로 가기가 연결된다.
- 큰 화면과 모바일 각각 적절한 밀도를 갖는다. 빈 공간 때문에 의미 없는 지표를 추가하지 않는다.

### 거래·데이터

- 정상: 계정 → 견적 → 승인/서명 → 입금 → 취득/보유 → 회수 → 지급 → 이력 대조.
- 예외: 잔액 부족, 만료, 거절, 다른 네트워크, 계정 변경, 응답 단절, 부분 처리, 지급 지연, 중복 클릭, 재접속.
- 없는 값은 0이 아니고 오래된 값은 최신 값처럼 보이지 않는다. NAV와 실행 견적을 구분한다.
- 완료·자동 검증·모션의 성공 상태는 실제 확인 결과를 반영한다.
- 의미 있는 상태·거래 테스트를 추가한다. 변경 없는 백엔드나 단순 스타일의 반복 검사를 늘리지 않는다.

### 실제 사용자 과제

구현 후 가능하면 제품을 처음 보는 사람에게 다음 과제를 요청하고 막힌 지점을 기록한다. 사람에게 확인하기 전에는 사용성 검증 완료로 표시하지 않는다.

1. 어떤 상품이며 무엇으로 구성되는지 설명하기.
2. 투자 전 비용·회수 조건 찾기.
3. 진행 중인 거래가 어디까지 처리됐는지 찾기.
4. 보유 자산과 처리 중인 금액 구분하기.
5. 회수 후 받을 자산과 지급 상태 찾기.

## 13. 경로 전환·배포

| 이전 경로 | 목표 경로/처리 |
| --- | --- |
| `/` | 새 Markets 홈 |
| `/?app=select` | `/products/ustx` |
| `/?app=portfolio` | `/lab`의 기존 모의 포트폴리오. 실제 `/portfolio`로 오인 이전하지 않음 |
| `/etfs/[slug]` | `/lab/strategies/[slug]`와 연결, 모의 데이터 유지 |
| `/proof` | 상품별 Transparency로 연결. 자주 쓰는 앵커도 대응 |
| `/?app=operations` | 권한 경계를 보존한 운영 전용 경로 |

프로토타입·fixture는 로컬 검수용이다. 실제 자산·거래 연결이 없는 상태를 완성된 제품처럼 운영에 노출하지 않는다. 단계별 프리뷰는 가능하나 주 고객 동선 전환은 최소한 상품·계정·거래·보유의 의미가 맞물릴 때 한다.

배포 시 최신 통합 브랜치와 현재 Worker를 비교하고 보안 수정·환경 변수·스케줄을 보존한다. 새 빌드와 필요한 검사 후 소스·Worker 버전을 기록한다. 문제가 생기면 호환되는 이전 UI로 되돌릴 수 있게 하되 실제 거래 기록·진행 주문을 삭제해 되돌리지 않는다.

이번 요청의 산출물은 상세 계획서이다. 새 화면 구현, 실제 자금 수령, 거래 실행, 계약 재배포는 수행하지 않았다.
